# Running on Oracle and PostgreSQL

The service runs unchanged on PostgreSQL (local development) and Oracle Database (CI, against
`gvenzl/oracle-free:23-slim`). Nothing in the Java code branches on the database vendor. This is the
list of decisions that make that true.

## Schema

| Decision | Why |
|---|---|
| Flyway `locations: classpath:db/migration/{vendor}` with `postgresql/` and `oracle/` folders holding the same versions, tables, columns and constraint names | DDL types differ; DML and queries do not. The two V1/V2 files differ only in type names, which a reviewer can check with a word diff |
| `BIGINT` / `NUMBER(19)`, `INTEGER` / `NUMBER(10)`, `VARCHAR` / `VARCHAR2` | Same value ranges on both; every Java `long` fits `NUMBER(19)` |
| `GENERATED BY DEFAULT AS IDENTITY` | Supported by PostgreSQL 10+ and Oracle 12c+. No sequences to keep in step, and the code never reads a generated key back (Oracle returns `ROWID` unless the key column is named, so avoiding it removes a driver difference) |
| `TIMESTAMP WITH TIME ZONE` for instants, bound as `OffsetDateTime` in UTC and read with `getObject(col, OffsetDateTime.class)` | JDBC 4.2 mapping that both pgjdbc and ojdbc11 implement; neither maps `Instant` directly |
| `DATE` for business dates, bound and read as `LocalDate` | Oracle `DATE` carries a time, which is always midnight here because only `LocalDate` is ever written |
| UUIDs stored as `VARCHAR(36)` | Oracle has no UUID type |
| No `BOOLEAN` columns | Oracle has them only from 23ai; the schema should not need the newest release |
| `CHECK (... IN (...))` instead of enum types | PostgreSQL enums have no Oracle equivalent |
| Column and table names avoid reserved words (`date`, `number`, `comment`, `level`, `size`, `user`, `offset`...): `business_date`, `record_type`, `amount_minor` | Oracle and PostgreSQL reserve different sets |
| Every identifier, constraint and index name is 30 characters or fewer | Oracle before 12.2 limits identifiers to 30 bytes |
| One `INSERT` per seed row, no multi-row `VALUES` | Multi-row `VALUES` is not Oracle syntax before 23ai |
| No apostrophes in SQL comments | Keeps both Flyway statement parsers out of quote-tracking edge cases |
| No triggers, no stored procedures | Nothing vendor-specific to port |

## Queries

| Decision | Why |
|---|---|
| All SQL is in `JdbcClient` with named parameters | One statement text per query, readable in review |
| Pagination with `OFFSET :offset ROWS FETCH NEXT :size ROWS ONLY` | ANSI SQL:2008; PostgreSQL and Oracle 12c+ both accept bind variables there. No `LIMIT`, no `ROWNUM` |
| Table aliases without `AS` (`FROM interchange_rate r`) | Oracle rejects `AS` before a table alias |
| `GROUP BY` repeats the columns, never an alias or position | Oracle allows aliases in `GROUP BY` only from 23ai |
| `COALESCE((scalar subquery), :default)` for the default interchange category | Standard on both; no `NVL`, no `IFNULL` |
| No upsert. Idempotency is "insert and let the unique key decide": `DuplicateKeyException` is what Spring translates both ORA-00001 and SQLSTATE 23505 to | `ON CONFLICT` and `MERGE` behave differently enough that one would leak vendor detail into the code |
| `SUM` results read with `getLong` and only over non-empty groups | `SUM` of no rows is `NULL` on both; `GROUP BY` never produces an empty group |
| Text ordering is done in Java (`Position.REPORT_ORDER`), not `ORDER BY` | PostgreSQL sorts by the database collation, Oracle by `NLS_SORT`; the report must be byte-identical on both |
| `IN (:ids)` lists are capped by `cardrail.settlement.chunk-size <= 1000`, validated at startup | Oracle allows at most 1000 expressions in an `IN` list (ORA-01795) |
| No empty strings are ever written: required text is validated as non-blank on arrival | Oracle stores `''` as `NULL`, so an empty string would hit a `NOT NULL` constraint on Oracle only |
| No nulls bound without a type | Spring falls back to `setNull(Types.NULL)` when it cannot learn a parameter type, which drivers handle differently; no statement here binds a null |

## Spring Batch

| Decision | Why |
|---|---|
| `spring.batch.jdbc.initialize-schema=always` | Spring Boot picks `schema-postgresql.sql` or `schema-oracle.sql` from Spring Batch; errors from tables that already exist are ignored, so restarts are safe |
| Flyway migrates before the Batch DDL runs | Boot orders Flyway ahead of script-based initializers, so Flyway always sees an empty schema on a fresh database (verified on PostgreSQL; the ordering is not vendor-dependent) |
| Paging reader built with `JdbcPagingItemReaderBuilder` and no explicit query provider | Spring Batch detects the database and generates `LIMIT` paging on PostgreSQL and `ROWNUM` paging on Oracle; the sort key is `id`, so paging is keyset-based on both |
| Job parameter `businessDate` is a `LocalDate` | Stored by Spring Batch as text with its type, identical on both |
| Default `isolation-level-for-create` (`SERIALIZABLE`) kept on Oracle | Spring Batch 5.2's Oracle DDL creates its tables with `SEGMENT CREATION IMMEDIATE`, which avoids the ORA-08177 seen with deferred segments. If it appears anyway, set `spring.batch.jdbc.isolation-level-for-create=read_committed` |

## How the suite selects Oracle

`ClearingDbProfileResolver` activates the profiles `test,oracle` when `CLEARING_DB=oracle`, otherwise
`test`. `application-oracle.yml` points at `jdbc:oracle:thin:@//localhost:1521/FREEPDB1` as
`cardrail`/`cardrail`; the `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME` and
`SPRING_DATASOURCE_PASSWORD` environment variables override it, as they override any Spring Boot
property. The tests are the same classes on both databases.

A GitHub Actions job for it looks like this:

```yaml
  clearing-oracle:
    runs-on: ubuntu-latest
    services:
      oracle:
        image: gvenzl/oracle-free:23-slim
        env:
          ORACLE_PASSWORD: oracle
          APP_USER: cardrail
          APP_USER_PASSWORD: cardrail
        ports: ["1521:1521"]
        options: >-
          --health-cmd healthcheck.sh
          --health-interval 10s --health-timeout 5s --health-retries 30
    env:
      CLEARING_DB: oracle
      SPRING_DATASOURCE_URL: jdbc:oracle:thin:@//localhost:1521/FREEPDB1
      SPRING_DATASOURCE_USERNAME: cardrail
      SPRING_DATASOURCE_PASSWORD: cardrail
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: "21", cache: maven }
      - run: mvn -B -pl cardrail-clearing -am verify
```
